本文档用于持续记录阅读、运行和测试 `wangcai_cpp` 时发现的问题。

## BUG-001：DemoStrategy 总下单数始终显示为 0

- 状态：`已确认 / 待修复`
- 影响范围：演示策略统计输出
- 严重程度：低；不直接影响订单提交和撮合，但会误导使用者
- 发现方式：运行以下样例回测后检查演示策略统计：

```bash
./build/backtest_main 000027.SZ 2022-01-07 logs
```

### 现象

`DemoStrategy` 已在阶段 0 提交 5 个订单、阶段 1 提交 5 个挂单，但最终显示：

```text
总下单数: 0 (目标: 10个)
```

同时阶段状态显示：

```text
阶段0-下单回调: 完成(5个订单)
阶段1-挂单演示: 完成(5个挂单)
```

### 原因

`DemoStrategy` 的成员变量 `order_counter_` 在构造函数中被初始化为 0，最终统计也读取该变量，但创建策略订单时没有递增它。

订单生成流程使用各演示函数内部的 `static int demo_count` 控制数量，它与成员变量 `order_counter_` 没有关联。因此实际生成了订单，统计值仍然保持为 0。

### 预期行为

每成功生成一条策略下单请求时，应更新统一的下单计数。当前演示流程完成后应显示：

```text
总下单数: 10 (目标: 10个)
```

这里统计的是“策略生成并提交给 BacktestEngine 的订单请求数”，不等同于订单被接受数或成交数。

### 建议修复

在订单加入返回事件列表时统一执行：

```cpp
events.emplace_back(order);
++order_counter_;
```

更稳妥的长期方案是区分以下计数，避免“下单数”的含义不清：

```text
submitted_order_count   策略产生的下单请求数
accepted_order_count    引擎校验并接受的订单数
rejected_order_count    校验失败或被拒绝的订单数
filled_order_count      发生过成交的订单数
cancelled_order_count   成功撤销的订单数
```

### 验证方法

修复后重新运行样例，检查：

1. `总下单数` 是否为 10；
2. 阶段 0 和阶段 1 各贡献 5 笔；
3. 计数修改不改变成交量、撤单数和持仓；
4. 若某笔订单被引擎拒绝，提交数仍增加，但接受数和拒绝数应分别正确记录。

## BUG-002：`load_orders_from_csv()` 创建了未使用的 Order

- 状态：`已确认 / 待修复`
- 影响范围：历史委托加载、订单 ID 映射和额外对象创建
- 严重程度：中

### 现象

`load_orders_from_csv()` 把 `csord` 行转换为 `Event(source="ord")` 后，还调用一次：

```cpp
auto order = order_book.createOrder(...);
```

该局部订单没有进入撮合引擎或价格桶。真正参与撮合的订单，是 `BacktestEngine::run()` 处理该 Event 时再次创建的：

```text
加载阶段：CSV -> Event + 未使用的临时 Order
运行阶段：Event -> 再次创建正式 Order -> 撮合
```

### 原因与影响

这是早期“加载时直接创建订单”实现遗留的代码。当前架构已改为加载 Event、运行时创建 Order，但旧调用未删除。

`createOrder()` 还会写入 `sys2str_`、`str2sys_`、`input2sys_` 和 `sys2input_`。临时订单销毁时映射不会自动清理，可能留下无效系统 ID、造成映射覆盖和调试混淆，并产生额外构造及映射写入开销。

### 预期行为与建议修复

```text
加载阶段：CSV 行 -> Event -> whole_events
运行阶段：Event -> 正式 Order -> 对应撮合引擎
```

删除加载器中未使用的 `order_book.createOrder(...)`；保留深市特殊订单所需的 `first_trade_px_` 等轻量预处理。长期可拆分对象构造与 ID 映射注册职责。

### 验证方法

1. 无策略样例的开盘价、收盘价、成交量和交易记录保持一致；
2. 历史撤单仍能根据原始订单 ID 找到正式订单；
3. 正式订单双向 ID 映射正确；
4. 加载完成、尚未运行时不存在临时订单留下的无效映射。


## BUG-003：上海集合竞价返回价未按 `bestVol/bestDiff` 过滤候选集合

- 状态：`已确认 / 待修复`
- 影响范围：`CallAuctionEngine::calcPredict_SH()` 的预测价及集合竞价结算价
- 严重程度：高；可能导致返回价格与最大可成交量不对应

### 现象

函数会计算 `bestVol`、`bestDiff` 和 `bestIdx`，但遍历时把所有满足基础 `tradable` 条件的价格都加入 `tradable_prices`，最终没有按最佳成交量和最小差值过滤，而是直接对全部价格求平均并返回 `rounded`。

需要说明：`bestVol` 是成交量，不是价格，本来就不应作为返回值。问题是返回的 `rounded` 可能包含成交量不是最大值、剩余量差也不是最小值的价格。

### 潜在后果

- `_predict_vol = bestVol`，但返回的 `_predict_px = rounded` 可能对应另一组可成交量；
- 预测价格和预测成交量不再属于同一个最终候选结果；
- `settle()` 可能使用未满足最终优先级的价格撮合；
- 上海开盘或收盘预测结果可能偏离预期规则。

### 预期行为与建议修复

```text
满足基础成交条件
-> 最大可成交量
-> 最小买卖剩余量差
-> 对最终仍并列的候选价格按上海规则定价
```

遍历时保存每个候选价格的 `tradable_volume` 和 `diff`，先求出 `bestVol/bestDiff`，再只保留同时满足两者的价格，最后求平均并进行 tick 对齐。修复前应使用人工订单簿和真实集合竞价结果再次确认规则细节。

### 验证方法

1. 构造多个基础可成交价但成交量不同的订单簿，只保留最大成交量候选；
2. 构造成交量相同但剩余量差不同的订单簿，只保留最小差值候选；
3. 构造最终仍有多个并列价的订单簿，验证平均与 tick 对齐；
4. 验证返回价格处重新计算的可成交量等于 `_predict_vol`；
5. 对比上海样例预测结果与真实数据。


## BUG-004：沪深集合竞价累计量算法不一致，活跃索引优化未实现

- 状态：`已确认 / 待评估`
- 影响范围：`calcPredict_SZ()`、`calcPredict_SH()` 的性能、注释准确性和后续维护
- 严重程度：中；目前主要是性能和可维护性风险，不能仅因实现不同判定计算结果错误

### 现状

两个函数都会通过 `for (int idx = 0; idx < N; ++idx)` 遍历涨跌停区间内的每一个合法价格 tick，但累计量算法不同：

- 深圳：每个 tick 使用 Fenwick Tree 的 `prefixSum()`，完整计算约为 `O(N log N)`；
- 上海：每次预测先构造 `buy_cumu/sell_cumu`，随后每个 tick 做 `O(1)` 查询，完整计算约为 `O(N)`。

上海函数上方注释声称只遍历 `_active_idx`，复杂度为 `O(M log N)`，但当前代码仍扫描 `0..N-1`，类中也没有对应的 `_active_idx` 成员及 `accept()/cancel()` 维护逻辑。

### 问题

- 注释与实际实现不一致，容易误导性能分析；
- 两个市场维护同一套 Fenwick 数据，但上海预测函数没有使用它；
- 深圳在全 tick 扫描中反复执行 Fenwick 查询，复杂度高于累计数组方案；
- 深圳循环内重复查询全市场总量，存在额外开销；
- 直接只遍历有订单的活跃价格，可能遗漏相邻活跃价格之间无挂单但仍可成为集合竞价成交价的 tick。

### 预期行为与建议

先保证沪深各自定价规则正确，再明确选择并记录累计量实现：

```text
方案一：完整 tick 扫描 + 左右累计数组，O(N)
方案二：活跃价格/区间 + Fenwick，目标 O(M log N)
```

若采用方案二，必须处理活跃价位之间的空价格区间，不能简单只遍历买卖量非零的下标。建议先修正失效注释并做性能基准；若 `N` 较小，优先使用简单、易验证的完整扫描累计数组。

### 验证方法

1. 覆盖只有少数活跃价格、但中间存在大量空 tick 的订单簿；
2. 验证空 tick 仍可能成为候选成交价；
3. 比较全扫描与优化算法在每个事件后的预测价和预测量；
4. 分别统计 SH/SZ 的耗时、Fenwick 查询次数和扫描价位数；
5. 确认新增、撤单、结算及收盘 bootstrap 后活跃索引一致。


## BUG-005：收盘集合竞价允许历史撤单，与普通股票规则不符

- 状态：`已确认 / 待修复`
- 影响范围：`BacktestEngine::run()`、`CloseAuctionEngine::cancel_by_input_id()`、`CloseAuctionEngine::cancel()`
- 严重程度：高

### 现象与原因

进入 `closing_mode_` 后，遇到 `Event(source="tra")` 会直接调用 `close_engine_->cancel_by_input_id()`。该函数继续调用 `cancel()`，真正删除订单、扣减价格桶和 Fenwick 数量，并回调撤单成功。

普通股票在 14:57～15:00 收盘集合竞价期间只接受申报，不接受撤销申报；当前调用链没有时间或品种规则校验。仓库现有样例数据在该时段没有撤单记录，因此暂未触发，但代码路径真实存在。

### 预期行为与建议修复

在 `BacktestEngine` 的事件路由层按市场、证券类型和时间判断撤单是否合法。普通股票 14:57～15:00 的历史撤单应被拒绝或作为异常数据记录，不能修改订单簿。引擎层也可增加防御性规则校验，避免被其他调用方绕过。

### 验证方法

1. 构造 14:56:59 的撤单，验证仍按连续竞价规则处理；
2. 构造 14:57:00～15:00:00 的撤单，验证被拒绝且盘口不变；
3. 检查拒绝原因、Fenwick、桶数量和 ID 映射均正确；
4. 对特殊品种使用独立规则测试，避免把普通股票规则硬编码到所有证券。

## BUG-006：收盘阶段策略下单和撤单仍被路由到连续竞价引擎

- 状态：`已确认 / 待修复`
- 影响范围：`processUserOrder()`、`processUserCancel()`
- 严重程度：高

### 现象与原因

收盘阶段的状态为：

```text
continuous_mode_ = true
closing_mode_ = true
```

但策略撤单只判断 `continuous_mode_`：

```cpp
if (continuous_mode_) {
    con_engine_->cancel(system_order_id);
} else {
    call_engine_->cancel(system_order_id);
}
```

因此不会调用 `CloseAuctionEngine`。策略下单也始终将未立即成交订单送入 `con_engine_->accept()`，没有根据 `closing_mode_` 路由或拒绝。

### 预期行为与建议修复

建立明确的交易阶段枚举，例如 `OpenCall / Continuous / CloseCall / Finished`，策略订单和撤单都根据同一个状态机处理。普通股票在收盘集合竞价期间可以按规则接受新申报，但撤单必须拒绝；策略订单若需要参与收盘集合竞价，应送入 `CloseAuctionEngine`，不能继续走连续竞价引擎。

### 验证方法

1. 14:56:59 的策略订单进入连续竞价引擎；
2. 14:57:00 后的合法策略新申报进入收盘集合竞价引擎；
3. 14:57:00～15:00:00 的策略撤单被拒绝；
4. 15:00 后的普通竞价策略事件被拒绝；
5. 检查回调中的接受、拒绝原因和订单状态一致。

## BUG-007：缺少明确的 15:00 收盘结算点和盘后交易状态

- 状态：`已确认 / 待修复`
- 影响范围：`BacktestEngine::run()` 的时间状态机、收盘结算及 15:00 后事件处理
- 严重程度：高

### 现象与原因

当前代码只定义 09:25 和 14:57 两个切换点，没有 15:00 的结算常量。第一次遇到时间不早于 14:57 的事件后进入 `closing_mode_`，随后所有剩余事件都按收盘集合竞价处理；`close_engine_->settle()` 仅在整个事件循环结束后调用。

因此收盘集合竞价没有在 15:00 明确结束。如果输入包含 15:00 后事件，它们可能被错误地继续纳入收盘集合竞价。代码或文档中的 15:30 注释还可能把收盘集合竞价与盘后固定价格交易、大宗交易成交确认时段混淆。

### 预期行为与建议修复

普通竞价交易状态机应明确为：

```text
14:57 进入 CloseCall 并 bootstrap
15:00 执行 close_engine_->settle()
15:00 后进入 Finished
```

如需支持 15:00～15:30 的盘后固定价格交易或大宗交易，应增加独立状态、事件类型和撮合实现，不能继续复用 `CloseAuctionEngine`。不同板块和证券类型的适用时段应配置化。

### 验证方法

1. 构造 14:59:59、15:00:00 和 15:00:01 的边界事件；
2. 验证收盘集合竞价只结算一次且结算时间明确为 15:00；
3. 验证 15:00 后普通竞价订单不会进入 `CloseAuctionEngine`；
4. 输入文件没有恰好 15:00 事件时，也必须由状态机完成结算；
5. 如实现盘后交易，分别测试收盘竞价与盘后固定价格交易的订单簿和成交记录。


## BUG-008：存在两套权威持仓，更新路径不一致

- 状态：`已确认 / 待修复`
- 影响范围：策略成交回调、持仓展示、最终 PnL 和结果统计
- 严重程度：高

### 现象

当前同时维护两套策略持仓：

```text
BacktestEngine::positions_
-> strategy_id -> symbol -> Position
-> 用于最终持仓、平均成本、已实现/未实现盈亏和 PnL 报告

Strategy::position_manager_
-> symbol -> int64_t quantity
-> 用于策略回调中的 deltapos、getPosition()/getAllPositions()
   以及 DemoStrategy 的持仓汇总
```

两者都被当作当前持仓来源，但更新入口不同：

- `BacktestEngine::positions_` 由 `BacktestEngine::updatePosition()` 更新；
- `Strategy::position_manager_` 由 `createTradeCallback()` 调用 `strategy->updateStrategyPosition()` 更新。

### 已确认的不一致路径

`tryFillImmediately()` 的立即虚拟成交只创建 `TradeCallback`，因此更新 `Strategy::position_manager_`，但没有调用 `BacktestEngine::updatePosition()`。通过 OrderBook `Execution` 回调产生的策略成交则可能同时更新两套持仓。

因此同一组策略成交可能导致：

```text
DemoStrategy 显示持仓 != BacktestEngine 最终报告持仓
策略回调 deltapos      != PnL 使用的 quantity
```

### 潜在后果

- 策略根据错误持仓继续下单；
- 最终持仓与策略内部持仓不一致；
- 平均成本和已实现/未实现盈亏基于不完整成交计算；
- 回测统计、风险限制和 PnL 结果互相矛盾；
- 新增成交路径时容易只更新其中一套。

### 预期行为与建议修复

应建立唯一权威持仓账本。推荐由 `BacktestEngine` 或独立 `PortfolioManager` 统一完成每笔成交的原子更新：

```text
Execution/Fill
-> 更新唯一 Position
-> 生成只读持仓快照
-> 构造 TradeCallback
-> 通知 Strategy
```

策略不应自行维护第二份可变权威持仓；`getPosition()` 可读取引擎提供的快照。如果为了兼容保留 `StrategyPositionManager`，也必须通过同一个统一成交入口同步，并增加一致性断言。

### 验证方法

1. 分别测试立即成交、挂单后成交、部分成交、平仓和反向开仓；
2. 每次回调后断言两种持仓口径一致，直至移除重复账本；
3. 验证 `TradeCallback::deltapos` 等于最终 Position 的 quantity；
4. 验证最终 PnL 使用了全部策略成交；
5. 多策略、多证券场景下确认持仓按 strategy_id 和 symbol 正确隔离。
